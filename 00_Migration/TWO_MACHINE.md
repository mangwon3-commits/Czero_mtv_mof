# 랩탑을 두 번째 계산 노드로 쓸 수 있는가

> 검토 2026-08-07. 결론부터: **지금의 병목에는 도움이 안 되고, 다음 단계부터는
> 확실히 도움이 됩니다.** 그리고 붙이기 전에 반드시 통과시켜야 할 검증이 하나
> 있습니다.

---

## 1. 지금 병목에는 왜 도움이 안 되는가

남은 수분 6작업은 **각각이 20~30시간짜리 단일 프로세스**입니다.

```
rh25_saIm100  rh50_saIm075  rh50_saIm100
rh90_saIm050  rh90_saIm075  rh90_saIm100
```

RASPA 한 작업은 단일 스레드라 **기계를 더 붙여도 한 작업이 빨라지지 않습니다.**
6작업이 이미 병렬로 돌고 있으므로 총 소요는 "가장 긴 작업 하나"로 결정됩니다.

랩탑에 2작업을 넘긴다면 그 작업들을 **처음부터 다시** 시작해야 하고(진행 중인 것을
이관할 방법이 없습니다), 랩탑은 데스크탑보다 느립니다. **순손실입니다.**

---

## 2. 어디서는 확실히 도움이 되는가

작업 수가 많고 서로 독립적인 단계입니다.

| 단계 | 작업 수 | 분할 적합성 |
|---|---|---|
| **아릴 GCMC** (남은 것) | **27** | 매우 좋음 — 전부 독립 |
| 작업용량 VSA/TSA (`NEXT_STEPS` 2-1) | 조성 5 × 조건 2 이상 = **10+** | 매우 좋음 |
| 아릴 계열 LAMMPS 안정성 (`NEXT_STEPS` 2-3) | **12** | 좋음 |
| 새 링커 스크리닝 | 수십 | 매우 좋음 |
| 밀도맵 | 10 | 좋음 (단 VTK 가 커서 전송 비용) |
| 수분 경쟁 | 6 (실행 중) | **부적합** — 위 1절 |

**가장 큰 이득은 아릴 GCMC 와 작업용량입니다.** 특히 작업용량은 아직 시작도 안 했고,
"목표대 진입"을 성능 주장으로 만들려면 반드시 필요한 계산입니다.

## 3. 붙이기 전에 반드시 할 것 — 동일성 검증

**이게 이 문서에서 가장 중요한 부분입니다.**

두 기계가 같은 물리를 계산한다는 보장이 없습니다. RASPA 빌드가 다르거나 힘장 파일이
한 줄이라도 다르면 **크래시가 아니라 조금 다른 숫자**가 나오고, 두 기계 결과를 한 표에
섞는 순간 그 차이가 조성 차이로 오독됩니다.

**절차:** 두 기계에서 **완전히 같은 작업 하나**를 돌리고 1.5σ 안에서 일치하는지 봅니다.

```bash
# 양쪽에서 동일하게
cd ~/mof_project/21_ZIF69_MTV
python -c "print(open('charged/base_DDEC6.cif').read()[:200])" | md5sum   # 입력 동일성
# 그리고 base 조성 0.15 bar CO2 GCMC 15000 사이클 1작업
```

기준값(데스크탑): **base 로딩 0.6800 ± 0.0111 mol/kg**, Q_st 21.08 ± 0.08.

> **전례가 있습니다.** 데스크탑 이전 때 노트북 값을 재현하는 검증을 했고 전부 1.5σ
> 미만이었습니다(`PART5_DRAFT.md`). 같은 방식을 그대로 씁니다.

함께 확인할 것:

| 항목 | 확인 방법 | 왜 |
|---|---|---|
| RASPA 버전 | `simulate -v` | 데스크탑은 2.0.41 (2021) |
| `UFF_MOF` 힘장 | `md5sum $RASPA_DIR/share/raspa/forcefield/UFF_MOF/*` | 한 줄만 달라도 값이 갈림 |
| `water.def` | `md5sum 19_WaterCompetition/water.def` | 3원자짜리면 알짜전하 +0.482 |
| 전하 CIF | `md5sum charged/*_DDEC6.cif` | PACMAN 재실행하면 미세하게 달라짐 |

**전하는 재계산하지 말고 데스크탑 파일을 그대로 복사하세요.** 랩탑에는 CUDA 가
없어서(MIGRATION §6) PACMAN 이 CPU 로 돌아 느린 데다, 재계산하면 동일성이 깨집니다.

## 4. 아직 모르는 것 — 랩탑에서 확인해야 합니다

저장소에 랩탑 사양이 **기록돼 있지 않습니다**(`PART5_DRAFT.md` 표의 노트북 CPU 칸이
비어 있음). 다만 간접 단서는 있습니다.

- 예전 스크립트가 `max_workers=6` 이었음 → **물리 6코어 안팎**으로 추정
- **CUDA 없음** — "노트북에는 없던 가속"(MIGRATION §6)
- ZIF-8 이원 GCMC 20작업을 워커 6으로 "2시간 이상" — 단 ZIF-8 은 셀당 276원자로
  ZIF-69(600원자)보다 훨씬 가벼워 직접 비교 불가

**랩탑에서 실행해 알려 주세요:**

```bash
lscpu | grep -E "^Model name|^Core\(s\)|^Socket|^Thread"
free -g | head -2
nvidia-smi -L 2>/dev/null || echo "GPU 없음"
~/miniconda3/envs/czeromof/bin/simulate -v
ls ~/mof_project 2>/dev/null | head -5 || echo "저장소 없음"
cd ~/mof_project 2>/dev/null && git log --oneline -1
```

특히 **노트북 지속 부하 시 발열 제한**을 봐야 합니다. 20시간짜리 계산에서
클럭이 절반으로 떨어지면 예상 소요가 두 배가 됩니다.

## 5. 전송 문제 — 이게 실질적 걸림돌입니다

**공유 파일시스템도 git 원격도 없습니다.** 현재 이 저장소는 이 기기 로컬 하나뿐이라
파일이 tar.gz 로 채팅을 거쳐 오갔습니다. 그 방식으로 두 기계를 상시 협업시키는 건
비현실적입니다.

권장 순서:

1. **GitHub 비공개 저장소를 하나 붙입니다.** 코드·설정·결과 JSON 만 오가면 되고
   용량은 작습니다(추적 파일 기준 수십 MB).
2. 큰 산출물(VTK, `Output/*.data` 30 MB짜리)은 **올리지 않습니다.** 이미 `.gitignore`
   대상이고, 필요한 건 결과 JSON 뿐입니다.
3. 원격이 생기면 어제 만든 `11_Novelty/coremof_check.py` 같은 도구도 양쪽에서
   똑같이 쓸 수 있습니다.

> 원격 저장소는 **이 기기가 유일한 사본**이라는 현재 위험도 함께 해결합니다.
> 랩탑에서 옮겨올 때 `.gitignore` 때문에 파일이 누락된 전례가 있습니다.

## 6. 분할 방식 — 동적 큐가 아니라 정적 분할

공유 파일시스템이 없으므로 **작업 큐를 공유할 수 없습니다.** 두 기계가 같은 큐를
보려 하면 같은 작업을 둘 다 잡습니다.

대신 **명시적으로 나눠 박습니다.**

```python
# run_aryl_gcmc.py 에 추가할 형태
MACHINE = os.environ.get('MOF_MACHINE', 'desktop')
SPLIT = {
    'desktop': ['nbIm025', 'nbIm050', 'nbIm075', 'nbIm100', 'mbIm025', 'brbIm025'],
    'laptop':  ['brbIm050', 'brbIm075', 'brbIm100', 'cf3Im025', 'cf3Im050', 'mslm025'],
}
tags = [t for t in ch['charged'] if t in SPLIT[MACHINE]]
```

결과 파일도 기계별로 분리해 씁니다 — `aryl_results_desktop.json`,
`aryl_results_laptop.json`. 합치는 것은 마지막에 한 번, 사람이 확인하면서 합니다.
**같은 파일에 양쪽이 쓰면 마지막에 쓴 쪽이 상대를 지웁니다.**

> 어제 데스크탑 안에서 두 세션이 같은 `aryl_runs/` 를 쓸 뻔한 사고가 있었고,
> 그건 같은 기계라 `/proc` 으로 막을 수 있었습니다(MIGRATION §3-10).
> **기계가 다르면 그 방어가 통하지 않습니다.** 정적 분할이 유일하게 안전합니다.
