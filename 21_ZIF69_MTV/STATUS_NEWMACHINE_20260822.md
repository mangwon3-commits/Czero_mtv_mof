## 2. ⚠️ 일감이 16작업이 아니라 4작업입니다

브리핑은 `run_water_v3grid.py` 로 **격자 4종 × RH 4단계 = 16작업**을
가정하고 있는데, **이 기기는 물리 4코어입니다**(`nproc` 4, Thread(s) per
core 1). 명세서 4-5절이 정확히 이 경우를 적어 두었습니다 —

> 코어가 4개 이하면 사용자에게 알리고 대상을 `saIm0583` 하나(4작업)로
> 줄이는 편이 낫습니다 — 승자 조성 하나만으로도 관문은 채워집니다.

사용자에게 알렸고 **saIm0583 한 종으로 축소하기로 결정**받았습니다.
16작업이면 네 파도 45~60시간인데, 4작업은 한 파도로 끝납니다.

### 그래서 아직 비어 있는 것

| 대상 | RH 스캔 | 어디서 |
|---|---|---|
| `saIm0583` | 🔄 이 기기에서 진행 중 (4작업) | 아래 3절 |
| `saIm0625` | ⬜ **미배정** | — |
| `saIm0667` | ⬜ **미배정** | — |
| `saIm0875` | ⬜ **미배정** | — |

**나머지 12작업은 여전히 갈 곳이 없습니다.** 명세서 §7 표의 "새 기기(당신)
= 16작업"은 이 회신 시점부터 4작업으로 읽어 주세요.

### 러너

새 러너를 만들지 않았습니다. `run_water_v3grid_0583.py`(커밋 `ab411c5`)는
`run_water_v3grid` 를 import 해서 경로·물 정의·워커 설정을 그대로 물려받고
`TARGETS` 만 `saIm0583` 으로 거르는 얇은 래퍼입니다. **엔진·사이클·힘장·물
정의는 한 글자도 다르지 않습니다.**

출력도 같은 `v3_water_grid/` 와 `water_runs_v3grid/` 를 씁니다. 그래서
나중에 누가 `run_water_v3grid.py` 로 16작업 전체를 돌리면 **여기서 완주한
4작업은 이어받기가 `cached` 로 건너뜁니다.** 중복 계산이 없습니다.

## 3. ⚠️ 이 기기는 임시 컨테이너입니다 — 결과를 전제하지 마세요

**계획에 반영하셔야 할 가장 중요한 항목입니다.**

이 세션은 사용자의 물리 기기가 아니라 **Firecracker 마이크로VM 클라우드
컨테이너**입니다. 근거:

- PID 1 = `/process_api --firecracker-init` (systemd/init 아님)
- 커널 `6.18.44-fc-v21 (builder@sandboxing)`
- 부팅 2026-08-22 03:56:21 — 세션 시작과 동시에 생성
- WSL 아님 · 호스트명 `vm` · root 실행 · 로그인 사용자 0명
- 저장소는 세션 시작 때 새로 clone (reflog 첫 줄)

비활성이 지속되거나 세션이 끝나면 **컨테이너가 회수되고 git 밖의 모든 것이
사라집니다.**

### 여기서 이어받기는 그물이 아닙니다

`water_results.json` 은 4작업이 **전부** 끝나야 쓰입니다
(`run_water.py:339`). 그전까지 진행분은 실행 폴더의 `.data` 로만 존재하고
이어받기는 그 파일을 읽습니다(`run_water.py:182`). **둘 다 이 컨테이너
디스크에만 있습니다.**

08-17 정전 때 19작업을 살린 그 메커니즘이 여기서는 작동하지 않습니다 —
**정전은 프로세스만 죽이고 디스크는 남지만, 컨테이너 회수는 디스크째
가져갑니다.**

### 대비책

1시간 간격 자가 점검을 걸어 두었고, 점검마다 완주한 작업이 있으면 러너
자신의 `parse_components` 로 값만 뽑아 `v3_water_grid/partial_snapshot_4core.json`
에 적고 커밋·푸시합니다. `.data` 는 건당 28 MB라 커밋하지 않습니다.
최악의 경우에도 **마지막 점검 이후 완주분만** 잃습니다.

**그러니 이 4작업이 반드시 도착한다고 가정하지 마시고**, 도착하면 얻는
것으로 잡아 주세요. 확실히 필요하면 지속되는 기기에서 다시 돌리는 편이
안전합니다.

실제 충돌은 없습니다 — 기기가 다르고 공유는 git 뿐이며, 러너가 작업 시작
시점에 CIF를 실행 폴더로 복사하므로(`run_water.py:190`) 이미 시작된 4작업은
저장소가 나중에 바뀌어도 영향받지 않습니다. 계산 중에는 `git pull` 을 쓰지
않고 `git fetch` 만 쓰고 있습니다(작업 트리를 건드리지 않기 위해).

다만 앙상블 작업이 `charged_v3/` 에 **기존 `saIm0583_DDEC6.cif` 를 수정**
하는 것이라면 알려 주세요. 새 파일(`saIm0583e{1..5}_DDEC6.cif`) 추가라면

## 7. 덧 — `bgstate.sh` 가 이 기기에서 거짓말을 합니다

여기서 `bash bgstate.sh` 를 돌리면 이렇게 찍힙니다:

```
부하 0.41 0.17 0.06 (물리 8코어)   메모리 가용 15 GB / 스왑 사용 0 MB
WSL 디스크  30G 여유 (20% 사용)
```

**4코어 비-WSL 기계에서요.** 189번 줄에 `"물리 8코어"`, 193번 줄에
`"WSL 디스크"` 가 하드코딩돼 있습니다. 데스크탑에서는 맞는 말이지만 다른
기기에서는 화면이 사실처럼 보이는 거짓이 됩니다 — CLAUDE.md 0절이 말하는
바로 그 유형입니다.

고치지 않고 보고만 합니다. 돌고 있는 스크립트를 편집하지 않는다는 규칙도
있고, 데스크탑에서 쓰는 값이라 그쪽이 판단할 일이라고 봤습니다. 다른 기기가
늘어난다면 `nproc` 과 `/proc/version` 에서 읽도록 바꾸는 것을 제안드립니다.
