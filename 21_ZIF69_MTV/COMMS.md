## 규약 — 여덟 줄

### ① 한 파일에 쓰는 사람은 하나

각 기기는 **자기 우편함만** 씁니다. 남의 파일을 고치지 않습니다.
그래서 병합 충돌이 **구조적으로 발생할 수 없습니다.**

```

21_ZIF69_MTV/COMMS/audit.md        <- 자동 일일 감사만 씀 (사람이 쓰지 않음)
```

읽는 것은 **누구나 전부** 읽습니다.

> 발송이 한 번 실패했습니다. 이름으로 부르는 경로는 언제든 끊깁니다.
> **git 이 정식 경로이고 직접 메시지는 보조입니다.**

### ② 자기 브랜치에 푸시하고, 읽을 때는 전부 가져온다

푸시는 자기 브랜치로 합니다(지시 없이 `master`에 푸시하지 않습니다).
대신 **읽는 쪽이 모든 브랜치를 가져옵니다.**

```bash
git fetch origin '+refs/heads/*:refs/remotes/origin/*'
git branch -r                                    # 어떤 기기가 있나
git show origin/<브랜치>:21_ZIF69_MTV/COMMS/<기기>.md   # 우편함 읽기
```

**`git pull` 을 쓰지 마세요.** 계산 중에 작업 파일이 바뀝니다. `fetch` 로
가져와서 `git show` 로 읽으면 작업 트리를 건드리지 않습니다.

### ③ 새 글은 맨 위에, 시각과 함께

우편함은 **역순 누적**입니다. 지운 글은 없습니다 —
"재계산 중"과 "폐기"를 구별하지 못해 데인 적이 있습니다.

```markdown
## 2026-08-22 14:30 — 제목 한 줄

**받는 곳**: cloud4c   ← 특정 기기 앞이면 명시, 전체면 생략
**요약**: 한 줄로.

본문.
```

### ④ 답이 필요하면 그렇게 적는다

```markdown
**답 필요**: 예 / 아니오
```

답이 필요한 항목은 상대 우편함에 답이 올라올 때까지 **가정하지 말고
비워 둡니다.** 이 프로젝트에서 가장 비싼 실패는 전부 "그럴듯하게 채워진 칸"
이었습니다.

### ⑤ 확인하지 못한 것은 **비워 두지 말고 "미확인"이라고 적습니다**

값을 읽지 못했을 때 추측으로 채우지 않는 것은 기본입니다. 그런데 **그냥
비워 두면 다음 사람이 "확인됨"과 구별하지 못합니다.** 빈칸은 "해당 없음"
으로도, "확인했고 문제없음"으로도 읽힙니다.

그래서 **비어 있다는 사실 자체를 값으로 적습니다.** 무엇을, 왜 못 읽었는지,
그것이 무엇을 위협하는지까지 씁니다.

**배정 규칙**: 기기의 관측된 연속 수명이 가장 긴 작업의 소요 시간보다
짧으면 그 작업을 주지 않습니다. 08-17 정전 때 19작업을 살린 이어받기는
**작업 경계**에서만 작동합니다 — 작업 내부에서는 그물이 없습니다.

> **단성분 점 하나로는 절반만 검증됩니다.** 물이 안 들어간 계산은
> 5자리 물·이원 Ewald·물 정의 복사 경로를 전혀 시험하지 않습니다.
> 배포본 3자리 물로 바뀌어도 그 점은 멀쩡히 통과합니다.

## 작업 비용 — 기기마다 재고, 배율을 옮기지 않습니다

08-22 에 랩탑이 `WriteBinaryRestartFileEvery 500` 을 시계로 써서 이원 GCMC
네 조건의 비용을 처음으로 **한 기기에서 전부** 쟀습니다. 정상 구간 2~3개
평균, 편차 ±1% 이내.

| 조건 | 500사이클 | 20,000사이클 환산 | RH0 대비 |
|---|---|---|---|
| RH0 (CO₂ 단성분) | 342 s | **3.80 h** | 1.0× |
| RH25 | 1239 s | **13.77 h** | 3.6× |
| RH50 | 1332 s | **14.80 h** | 3.9× |
| RH90 | 1574 s | **17.49 h** | 4.6× |

> 기기: 랩탑(물리 8코어, 8워커 동시 부하). **부하 조건까지 같이 적으세요** —
> 워커 수가 다르면 메모리 대역 경합이 달라져 값이 움직입니다.

> **배율은 기기 고유입니다. 옮기지 마세요.**

같은 RH0→RH90 배율이 외부 16코어에서는 **8배**(2.9→23.1 h), 랩탑에서는
**4.6배**입니다. 08-22 에 데스크탑이 외부 기기 배율을 랩탑에 적용해
RH90 을 30 h 로 추정했는데 실측은 **17.5 h** 였고, 그 오차가 일정표를
13시간 틀리게 만들었습니다. 더 나쁜 것은 방향입니다 — 완료 시각이 안전한
20:41 에서 재부팅 창 한가운데인 08:05 로 **옮겨간 것을 놓칠 뻔했습니다.**

## 진행 상황은 로그가 아니라 출력 파일로 셉니다

`run_water.py:300` 이 `ex.map(_star, jobs)` 로 도는데 **`ex.map` 은 결과를
제출 순서대로 내놓습니다.** 작업 순서가 조성별·RH 오름차순이라 네 번째
작업이 그 조성의 RH90(20시간대)입니다.

> **그래서 로그가 세 줄을 찍고 스무 시간 가까이 얼어붙습니다.** 그 사이
> 뒤쪽 작업이 완주해도 한 줄도 안 나옵니다.

CLAUDE.md 4절 함정의 세 번째 판입니다. 여기서 "멈췄다"고 판단해 죽였다
살리면 **진행 중이던 RH90 의 스무 시간이 통째로 날아갑니다** — 체크포인트는
배치만 복원하고 진행도는 복원하지 않습니다.

```bash
~/miniconda3/envs/czeromof/bin/python 21_ZIF69_MTV/water_progress.py
```

러너 자신의 `finished()` · `net_charge_ok()` 를 그대로 써서, 여기서 완료로
세는 것과 러너가 `cached` 로 건너뛰는 것이 항상 일치합니다.
